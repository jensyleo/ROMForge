# ROMForge — Identification States (ROM/CHD/Game)

Single reference document for all the logic behind "what state is this in and what message do we show?". This is the foundation for the future file-manipulation phase (rebuild/fix) — any decision about what to do with a file depends on first identifying, unambiguously, what state it is in.

It does not document the code itself (that lives in each file's doc-comments); it documents the **decision model**: what facts determine each state, and what we show the user in each case.

---

## 0. External sources — how MAME manages its own ROMs

ROMForge does not invent its own rules about what a "correct", "nodump", or "optional" rom is — all of that comes directly from the format MAME itself defines. These are the sources consulted, in order of reliability, highest to lowest:

1. **The DTD embedded in `-listxml` itself** (the first ~100 lines of any real MAME DAT, inside `<!DOCTYPE mame [...]>`). This is the most reliable source possible: it's generated by MAME itself, in the exact same version that produced the DAT you're using. This is where the `status="nodump"/"baddump"`, `merge="..."`, and `optional="yes"` attributes on `<rom>`/`<disk>` were confirmed — not from any third-party wiki. To see it yourself: `head -120 your_file.DAT` and look for `<!ELEMENT` / `<!ATTLIST`.
2. **MAME's own audit source code**, [`src/frontend/mame/audit.cpp`](https://github.com/mamedev/mame/blob/master/src/frontend/mame/audit.cpp) — how MAME itself decides whether a romset "passes" so it can run (the `audit_status`/`audit_substatus` enums, `ROM_ISOPTIONAL`/`FLAG_NO_DUMP` handling, sample logic). **Important design note:** MAME optimizes this for a single binary question ("can I run this game?"); ROMForge, being a collection manager/auditor, deliberately does NOT copy that collapse-to-a-single-boolean logic — it shows the real state of EACH individual file (row by row), even when MAME internally would consider it irrelevant to booting the game. This is an intentional divergence, not an oversight.
3. **MAME's command-line documentation** — [docs.mamedev.org/commandline](https://docs.mamedev.org/commandline/commandline-all.html) — `-listxml`, `-verifyroms`, `-verifysamples`, `-listsamples`.
4. **wiki.romvault.com** (`mame_listxml` and related pages) — useful as context for how another real tool (RomVault) consumes the same format, though it is not a normative reference for the format itself.

**Session rule (Aug 4-5, 2026):** any new special case is first verified against the user's real DAT (`mame0288.DAT`) with `grep`/`awk`/`python3` — never assumed to exist or to occur at a given frequency without counting it in the real file. When the real DAT has no available test case (e.g. the user does not own the Astron Belt collection), it is verified with a synthetic file (empty, only the correct name) against the real DAT — name/hash logic does not require real content to be tested.

## 1. The three state levels

There are three distinct levels, each with its own vocabulary. Do not mix them:

| Level | Swift type | Where it lives | What it's for |
|---|---|---|---|
| **Raw matcher result** | `RomMatchStatus` | `ROMForgeCore/Matcher/MatchReport.swift` | Output of `ROMMatcher.match()` — never persisted, never seen directly by the UI |
| **Audit status (persisted)** | `AuditStatus` | `ROMForgeCore/Reports/AuditReport.swift` | What gets saved in SQLite and what the UI shows for EACH individual rom or disk row |
| **Aggregated game state** | `AuditStatus` (same enum, reused) | `App/LibraryDetailView.swift` (`gameCategory`) | The icon/color of ONE game's row in the list, summarizing all its roms (or disks) |

---

## 2. Level 1 — Raw per-rom result (`RomMatchStatus`)

This is what `ROMMatcher.swift` decides for **each individual rom** of a game, comparing against the scanned files. It never reaches the UI as-is — it's always translated to `AuditStatus` (table §3).

| Case | Meaning | Triggered when |
|---|---|---|
| `.correct(file, viaHeaderStrip)` | Name and content match exactly | A file in the expected location (its own file/zip) has the correct hash AND the correct name |
| `.misnamed(file, viaHeaderStrip)` | Correct content, wrong name | The hash matches, but the file's name inside the zip differs from what's expected |
| `.foundElsewhere(file)` | The game **genuinely exists**, but this specific rom is in the wrong place | The rom is not in the game's own archive, BUT (a) the game does have at least one of its own roms claimed in its own archive, OR (b) the content is in a file that belongs to NO game in the DAT (a file renamed by the user) |
| `.hashMismatch(file)` | There's a file exactly where expected (same name, same file/zip), but its content is wrong | The name matches inside the file's own zip, but the hash doesn't |
| `.missing` | Genuinely absent, nowhere in the scan | None of the above applies — includes the case "the game doesn't exist at all" (see Note A) |

**Note A — the rule that took three attempts (Aug 4, 2026):** `.foundElsewhere` must NEVER trigger just because the content matches by size something from ANOTHER real game you own. It must mean *"you have this game, but one of its roms is misplaced"* — never *"you don't have this game, but another game contains roms that this one would also need."* See `ROMMatcher.swift`'s `gameOwnsRealFiles` for the exact implementation.

**`nodump`** (declared as such by the DAT, not a `RomMatchStatus` — it's `RomDumpStatus`): omitted from the report entirely, neither correct nor missing. MAME/ClrMamePro/RomCenter don't count it against completeness either.

## 3. Level 2 — Per-row audit status (`AuditStatus`)

5 values, used for both roms and disks (CHD). This is what's persisted in SQLite and what colors each individual row in the right-hand panel (detail of the selected game).

| `AuditStatus` | Color | Icon | Priority (worst→best) |
|---|---|---|---|
| `.missing` | 🔴 Red | `xmark.circle.fill` | 1 (worst) |
| `.badDump` | 🟠 Orange | `exclamationmark.octagon.fill` | 2 |
| `.incorrect` | 🟡 Yellow | `exclamationmark.triangle.fill` | 3 |
| `.correct` | 🟢 Green | `checkmark.circle.fill` | 4 (best) |
| `.surplus` | ⚪️ Gray | `questionmark.circle.fill` | — (not a severity, it's "unrecognized") |

### 3a. `RomMatchStatus` → `AuditStatus` mapping (roms)

| `RomMatchStatus` | `AuditStatus` | Row text (right panel) |
|---|---|---|
| `.correct` | `.correct` | "Ok" (or "Ok (header removed to match)" if header stripping applied) |
| `.misnamed` | `.incorrect` | "Bad name" |
| `.foundElsewhere` | `.incorrect` | "Available in another game (`<file>`)" |
| `.hashMismatch` | `.badDump` | "Bad (hash mismatch)" |
| `.missing` | `.missing` | "Missing" |
| (surplus file, no rom claims it) | `.surplus` | "Unrecognized" |

Additional modifier, independent of the state above: if the DAT itself declares the rom as `baddump`/`nodump` (`RomDumpStatus`, a fact about the *reference* dump, not about your local file):
- Any status except Missing: `"(bad dump in DAT)"` is appended to the text.
- Missing: instead, `"Missing (also a known bad dump in DAT)"` — never implying that something was found.

**Explicitly confirmed case (Aug 4, 2026): `.correct` + `isBadDump` → still GREEN, text "Ok (bad dump in DAT)".** This is not a contradiction or a bug — they are two independent facts that coexist:
- `entry.status == .correct` answers: *"does your local file match exactly what the DAT declares?"* → Yes.
- `entry.isBadDump` answers: *"does the DAT itself admit that its reference dump is defective/incomplete?"* → Yes, but that's a fact about the REFERENCE, not about your file.

The color always reflects the first question (`tint(for: entry.status)`, never `isBadDump`) because that's the only one that matters for deciding whether there's anything you can or should fix: if your file already matches the reference dump byte for byte — whether that dump is good or bad — there is no possible action on your part. A "better" file cannot exist because, by definition, the DAT doesn't know of a better one. The text in parentheses is purely informational (so you know that particular dump is known to be problematic in the MAME hobby in general), never an instruction to "fix this."

### 3b. Disk/CHD status (`DiskAuditor` + `CHDMatcher`)

A CHD has 4 possible states (never `.badDump`, never `.foundElsewhere` — it's verified by the header's SHA1, there's no "found elsewhere"):

| `CHDDiskStatus` | `AuditStatus` | Disk row text (left) |
|---|---|---|
| `.correct(url)` | `.correct` | "Correct" |
| `.incorrect(url)` | `.incorrect` | "Incorrect" |
| `.missing` | `.missing` | "Missing" |
| `.unverifiable(url)` | `.unverifiable` | "Nodump (unverifiable)" — see §4e3 |

**Fixed (Aug 5, 2026):** a `.chd` on disk that doesn't correspond to ANY disk declared by the DAT (for any machine) no longer disappears — `DiskAuditor.audit` now tracks which `.chd` files each disk claims (`.correct`/`.incorrect`/`.unverifiable`) and, at the end, any unclaimed `.chd` is reported as `.surplus` (`game: nil`, `isDisk: true`) — exactly the same mechanism that already existed for surplus roms, so the app layer (`gameNodes(from:)`) automatically groups it into its own "Unknown game" bucket with no additional changes. Verified live against a real case from the user: `cap-33s-22.chd` (in `CAPCOM/CPS3/BATOCERA/sfiii3`) doesn't match any `<disk>` in the real DAT — previously invisible, now appears as surplus. `AuditReportDatabase.currentSchemaVersion` bumped to v14.

### 3c. Recognized surplus vs. genuine surplus (`requiredByGameDescription`)

**Real case (Aug 4, 2026):** under Split, a clone (e.g. `sf2acc`) declares ONLY its unique roms — the ones it shares with its parent (`merge=` in the DAT) are excluded from its own list, because Split expects them to live only in the parent's archive. But the user's real `.zip` often DOES contain that shared content too (a valid, correct dump) — and since the per-file scan never looks inside `sf2acc.zip` for `sf2ce`'s (the parent's) roms, that file goes unclaimed by anyone and was reported as generic "Unrecognized," indistinguishable from actual junk.

**Fix (fixed twice the same day — final version):** before declaring a leftover file as surplus, its hash is compared against ALL roms in the DAT (from any game, without filtering by merge mode). If it matches something real, **it's genuinely reclassified as `.incorrect`**, not left as `.surplus` with just a color change — a correction from the user himself (Aug 4, 2026): "surplus" should mean *unknown*, and this case stops being that as soon as it's identified.

| Situation | `AuditStatus` | Color | Text (individual row) |
|---|---|---|---|
| Hash matches NOTHING in the DAT | `.surplus` | ⚪️ Gray | "Unrecognized" |
| Hash matches a rom from ANOTHER real game | `.incorrect` | 🟡 Yellow (native, unpatched) | "Not needed here (required by `<game>`)" |
| No hash (the rom doesn't have one), but the NAME matches a `nodump` rom in the DAT | `.unverifiable` | ⚪️ Gray (different icon) | "Nodump (unverifiable)" — see §4e2 |

The GAME-level message (left column) also distinguishes this case — within `.incorrect`, in priority order:
1. The whole file is misnamed → "Bad file name"
2. Some of the game's own ROMs are misnamed or found elsewhere → "Rom need fix"
3. Everything belonging to the game is fine; the only issue is an already-identified surplus file → **"Extra file, not needed here"**

**Consistency across views:** this file is "folded" into its game's row by matching the archive's filename (not by the `game` field, which stays `nil` for these entries) — in the "Database" view (`computeGameAggregateStatusByName`), in folder view (`gameNodes`), and in the header counts (`computeScopedStatusCounts`). All three fold it the exact same way, so they can never disagree with each other about a game's state.

Implemented in `ROMMatcher.match`'s `romsByHash`/`requiredByGameDescription` (identification) + `AuditReporter.generate` (reclassification to `.incorrect`) + the three folding points in `LibraryDetailView`. Never used to *claim* a file (it doesn't reopen the "theft between games" problem — it remains purely informational).

**Never "required by" the game itself (Aug 4, 2026):** if a file appears DUPLICATED inside its own game's archive (two physical copies of the same rom, one claimed and one surplus), `requiredByGameDescription` must never say that file is required "by" its own game — that makes no sense ("needed here" when it's literally already here). It's checked against the containing game's own roms (by filename) before consulting the global index; it's only reported when the real owner is a DIFFERENT game.

**Cache bug across scans with this same field (Aug 4, 2026):** a game whose entire footprint in a fresh scan is purely `surplus` (`game: nil` — e.g. `qsound_hle` under Split, where its only rom is `merge=`-tagged and entirely excluded from its own expected list) was never recognized as "touched" by `Self.merge()` in `LibraryViewModel.swift`, because that detection only looked at entries with `game != nil`. Result: an old, already-incorrect row (`.correct`, from a previous scan under a DIFFERENT mode where that rom was claimed) was kept without reconciling, appearing DUPLICATED alongside the fresh, correct row ("Not needed here") — two contradictory rows for the same rom. Fixed: any file with a real path within the scan's scope (recognized or not) marks as "touched" the game its own filename implies, regardless of whether the matcher ended up attributing it to `game: nil` or not. **Requires re-scanning the affected folder** — data already saved from a previous scan doesn't self-correct, only a new scan applies the fixed logic.

**Third bug, the definitive root cause (Aug 4, 2026, same day):** after fixing the duplicate, the resulting single row showed "Unknown game" (gray "?" icon) instead of "QSound (HLE)" in yellow. Cause: the "does this game genuinely exist?" check that decides whether a surplus file folds into a known game's row or becomes a separate "Unknown game" bucket was based on `gameAggregateStatusByName`/`entriesByGame` — dictionaries built **only from scan results** (`entry.game != nil`). A real DAT game whose expected rom list ends up at ZERO under the active merge mode (like `qsound_hle` under Split) never generates any entry with `game` assigned — so it never existed in those dictionaries, and its surplus file failed the existence check in all THREE places that perform it (`gameNodes`, `computeGameAggregateStatusByName`, `computeScopedStatusCounts`).

**Fixed:** the existence check now uses the DAT's real catalog (`gamesByName`, derived from `viewModel.preloadedGames` — every game the DAT declares, regardless of whether the scan produced any entry for it) in all three places, instead of the scan result. Additionally, each `GameNode` now receives `sourceGame` (the real `DATGame`) as a fallback for its title — so a game with no entry of its own carrying `gameDescription` (as in this case) still shows its real description ("QSound (HLE)") instead of its raw internal name ("qsound_hle").

### 3d. Complete case study: `qsound` / `qsound_hle` (sound chip shared across dozens of games)

Worth documenting this case in detail because it exposes, in one real example, exactly what all of §3c exists for — and because jensyleo himself caught an incorrect claim I made about it live (Aug 4, 2026), which is corrected below.

**The real facts of the collection** (mame0288.DAT + `CAPCOM/CPS1` and `CAPCOM/CPS2` folders):

- `qsound` is the "parent" machine — Capcom's QSound sound chip itself, declared in the DAT with its own rom `dl-1425.bin` (no `merge=`, it's the "original" reference copy).
- `qsound_hle` is a separate DEVICE machine (`isdevice="yes"`, `romof="qsound"`) — the HLE emulation of the same chip. It declares the SAME rom, but with `merge="dl-1425.bin"`: MAME explicitly says "this is the same rom as the parent's, don't duplicate it."
- Dozens of real CPS1 and CPS2 games (`1941`, `dino`, `punisher`, `wof`, `19xx`, `avsp`, `xmvsf`, `mvsc`, `ssf2`, `sfa`, etc. — any game that uses the QSound chip) each have their **own physical copy** of `dl-1425.bin` inside their own `.zip` — this is how "all-inclusive"/Un-merged romsets that people download are distributed.
- **Only `qsound.zip`** (located in the `CPS2` folder, not `CPS1`) exists as a file dedicated exclusively to the `qsound` machine.

**Verified byte for byte:** the `dl-1425.bin` inside `qsound_hle.zip` (CPS1) and the one in `qsound.zip` (CPS2) are identical (same MD5, `108b113a...`) — it's literally the same file, repeated in more than 25 different places in the collection.

**Under Split, scanning CPS1 + CPS2 together** (as they'd be configured for the same system):

| File | `dl-1425.bin` reports |
|---|---|
| `qsound.zip` (CPS2) | 🟢 `.correct` — this IS its declared home |
| `qsound_hle.zip` (CPS1) | 🟡 "Not needed here (required by QSound)" |
| `wof.zip`, `dino.zip`, `punisher.zip` (CPS1) | 🟡 "Not needed here (required by QSound)" |
| `19xx.zip`, `avsp.zip`, `xmvsf.zip`, `mvsc.zip`, `ssf2.zip`, `sfa.zip`... (CPS2, 20+ more) | 🟡 "Not needed here (required by QSound)" |

**My own mistake, corrected live:** in an initial analysis I claimed `qsound.zip` didn't exist in the user's collection at all — based on having only looked at the `CPS1` folder. jensyleo correctly pointed out that it did exist, and indeed it was in `CPS2`. This is practical proof of why `requiredByGameDescription` must be looked up against **the entire combined scan** (all of a system's folders), never against a single isolated folder — exactly the design already implemented (§3c), just confirmed here with a real large-scale case (25+ redundant copies of the same file).

### 3e. "Unknown game" (gray) vs. already-identified surplus file (yellow) — Merged case

**Real question from jensyleo (Aug 4, 2026):** under Merged, a clone (e.g. `sf2acca.zip`) is **entirely excluded** from `dat.games` (it's folded into its parent) — so its physical file, even though the matcher correctly identifies all its content (see §3c/3d), has no real game to fold into in the left-hand list. Before this fix, this ALWAYS showed as gray "Unknown game" — even though the right panel, row by row, already showed each rom in yellow "Not needed here." Gray and yellow contradicting each other for the exact same content.

**Rule decided:** "Unknown game" (gray) should honestly mean *"I have no idea what this is."* If **all** entries of a surplus file have `requiredByGameDescription` (i.e. the matcher identified which real game each one belongs to), the whole bucket is reclassified:

| Situation | Color | Text |
|---|---|---|
| At least one genuinely unrecognizable entry | ⚪️ Gray, `.surplus` | "Unknown game" |
| **All** entries identified (`requiredByGameDescription` on all of them) | 🟡 Yellow, `.incorrect` | "Extra archive, not needed here (required by `<game>`)" |

Controlled by the toggle matching its real color: a bucket reclassified to yellow responds to the "Incorrect" toggle, not the separate "Unknown" toggle — and the header's "Unknown: N" count no longer counts it (that would contradict its own color).

**Closed gap (Aug 4, 2026, same day):** this reclassified bucket now DOES count toward the header's "Incorrect: N" count. `computeScopedStatusCounts` applies the same `isFullyIdentified` criterion to any surplus file that fails to fold into a real game from `dat.games` (the Merged case) — if all its entries are identified, it counts as one more file under `.incorrect`, exactly like the row you see in the list. Header, row, and toggle are now synchronized for this case.

### 3f. A clone can have its own CHD distinct from its parent's — Merged must expect both

**Found while thoroughly reviewing the Merged code (Aug 4, 2026), not reported live by the user.** `MAMESetLayoutPlanner.mergedGame` already merged the unique roms of the whole family (parent + clones) into the surviving entry under Merged — but nobody did the same for **disks**. `DATLoader.datFile` took the `disks` field directly from the parent machine, ignoring the clones' own disks.

**Verified against the real DAT (mame0288):** **313 clones declare a CHD with a genuinely distinct SHA1 from their parent's** (a different disk revision/region) — not a rare case. Under Merged, since the clone is entirely excluded from `dat.games`, that CHD of its own was never expected by anyone: even if the user had the correct `.chd` file, it was reported as "Unrecognized" (genuine surplus), with no way to recognize it.

**Fixed:** new function `DATLoader.mergedDisks(for:mode:dataset:)` — under Merged, it merges the surviving game's own disks with those of **all its direct clones** (deduplicated by name+SHA1, since 91 of those 313 cases DO share the identical disk with the parent). Split/Un-merged don't need this change — there each clone still has its own entry in `dat.games`, with its own disk already captured directly.

**A second, related suspicion was ruled out:** are there "clone of a clone" chains (3 levels) that would break the `clones(ofParent:)` lookup (which only looks at direct children)? Verified: **zero cases** in the real DAT — MAME's convention always points `cloneof` directly at the true root, never at an intermediate clone. Not a real bug.

Verified live: `area51`/`area51t` — under Merged, the merged "area51" entry now correctly expects both disks.

## 4. Level 3 — Aggregated game state (left-hand game list row)

Each game can generate **up to 2 independent rows** in the game list: one for its roms, one for its CHD (`GameNode.isDiskRow`). Never mixed in the state calculation — jensyleo (Jul 30, 2026): "if the .zip is OK show it as Correct, but separate from the .chd."

### 4a. Aggregation rule (worst-of), same for roms and disk

```
gameCategory(entries) =
    if any entry == .missing   → .missing   (red)
    else if any entry == .badDump → .badDump (orange)
    else if any entry == .incorrect → .incorrect (yellow)
    else → .correct (green)
```

A single missing rom paints the ENTIRE game red (for that row — rom or disk, whichever has the problem).

### 4b. Database view vs. "Rom files" folder view (Aug 4, 2026, fixed)

**Current rule (single, no view-based exceptions):** "Missing" is calculated and shown the same way in both views. The difference between views is NOT "hide missing in folder view" — it's **where the aggregated entries come from**:

- **Database**: uses the full truth of the DAT (`gameAggregateStatusByName`) — a rom missing from the ENTIRE system paints the game red.
- **"Rom files" folder**: uses only the entries that survived the "does this game have something genuinely its own in this folder?" filter (`scoped(_:)`). This matters when a system has SEVERAL rom folders: if a game's rom lives in folder B, it shouldn't be painted red when viewing folder A just because it's not there — this isn't "hiding Missing," it's that this rom simply isn't `.missing` from this folder's point of view if it genuinely exists in folder B (see `merge()` in `LibraryViewModel.swift`, which reconciles results across scans of different folders).
- A game with NO file of its own in the current folder (phantom/unowned) **doesn't appear at all** in that folder — filtered out before reaching aggregation (`recomputeGamesInFolder`/`scoped(_:)`, specifically excludes `.foundElsewhere` content).

### 4c. Special case: a game with ROM + CHD, its own ROM is missing but the CHD is fine

**Explicit rule (confirmed Aug 4, 2026, after testing the alternative live):** if a game's CHD is `.correct` (or `.incorrect`, anything other than `.missing`) and ALL of that same game's rom entries are `.missing`, **the ROM row is not shown at all**. Only the disk row is shown (green/correct). The game appears 100% "Ok" in the game list.

- The opposite (showing the ROM row in red, separate) was tested the same day — discarded: a red row next to a green row for the same game caused more confusion than clarity.
- **Exception to the exception:** if the ROM is `.incorrect` (misnamed) or `.badDump` — i.e. there's something there, it's just wrong — the row IS shown, always. Only a *fully absent* ROM is hidden when the CHD compensates.
- The **header count** ("Missing: N") still counts this game as missing even though its row isn't shown — a known, pre-existing inconsistency (not introduced today), not fixed per the user's explicit decision not to touch more than what was asked.

### 4d. Game row messages (`GameNode.infoText`)

**Disk row** (`isDiskRow == true`):

| Aggregated state | Text |
|---|---|
| `.missing` | "Missing" |
| `.incorrect` | "Incorrect" |
| `.badDump` | "Bad" |
| `.correct` / `.surplus` | "Correct" |

**Rom row** (normal game):

| Aggregated state | Text | Distinction |
|---|---|---|
| `.missing` | "Incomplete (rom missing)" | — |
| `.badDump` | "Bad (hash mismatch)" | — |
| `.incorrect` | "Bad file name" | The whole ARCHIVE's name doesn't match the expected `<game>.zip` |
| `.incorrect` | "Rom need fix" | The archive's name is correct, but some rom INSIDE is misnamed |
| `.correct` (with some `.surplus` inside) | "Extra file in archive" | The zip has an extra file the DAT doesn't expect |
| `.correct` | "Ok" | Everything matches |

**"Unknown game" bucket** (`isSurplusBucket == true`): always "Unknown game," regardless of anything else — no real DAT game behind it.

**Before scanning** (`aggregateStatus == nil`): "Not scanned yet."

## 5. Header counts (filter buttons)

`computeScopedStatusCounts` — counts **games/files**, not individual roms, and is **rom-only**: the CHD's state never affects these 4 numbers (which is why a broken CHD doesn't change the "Incorrect" count if the same game's roms are fine).

| Button | Counts games whose ROM (not disk) aggregation is... |
|---|---|
| Correct: N | `.correct` |
| Incorrect: N | `.incorrect` |
| Bad: N | `.badDump` |
| Missing: N | `.missing` |
| Unknown: N | (separate — counts "Unknown game" buckets, not an `AuditStatus`) |

### 4e5. Orphan CHD vs. duplicate CHD — correctly distinguished (added Aug 5, 2026)

While implementing the "orphan CHD no longer disappears" fix (§4e3/TODO.md, same day), the user caught a real bug live: any `.chd` that existed in TWO distinct physical folders (their own real collection: `CAPCOM/CPS3/` and `CAPCOM/CPS3/BATOCERA/` — several CHDs mirrored in both) showed a duplicate gray "Unknown game" row next to the correct green row for the same file — the initial fix only distinguished "claimed" vs. "unclaimed," without recognizing that an unclaimed `.chd` could still be KNOWN content (a second physical copy of a disk the DAT does declare, just that the first copy already satisfies it).

**Fixed:** same pattern that `romsByHash`/`requiredByGameDescription` already uses for duplicate roms. `DiskAuditor.audit` now builds an index of ALL disk sha1s declared by the DAT (from any game), and when a surplus `.chd` goes unclaimed by anyone, it compares its own header sha1 against that index: if it matches, it's reclassified as `.incorrect` with `requiredByGameDescription` (rendering as "Not needed here (required by X)," the same text and folding logic already used for roms — with no changes to the app layer); if it matches nothing, it remains genuine `.surplus` ("Unknown game").

Verified live against the user's real CPS3 folder: 4 duplicate CHDs (`cap-sf3-3.chd`, `cap-3ga000.chd`, `cap-33s-1.chd`, `cap-33s-2.chd`, present in both folders) went from showing a phantom "Unknown game" to "Not needed here (required by ...)"; the single genuine orphan (`cap-33s-22.chd`, only in BATOCERA) correctly remained `.surplus`. `AuditReportDatabase.currentSchemaVersion` bumped to v15.

### 4e6. Duplicate ROM across different folders — fixed for roms, not just CHDs (added Aug 5, 2026)

After the duplicate CHD fix (§4e5), the user tested adding a duplicate ROM FILE (`sfiii2.zip`, same base name as the real one, in a different physical folder) and found that — unlike the CHD — the duplicate zip wasn't marked "Not needed here," it simply disappeared from the "surplus" view (though it also wasn't shown as "Correct" — the individual rom inside the zip appeared as genuine, unidentified surplus).

**Root cause:** `ROMMatcher.requiredByGameDescription` decided "is this surplus file actually the game's own archive (just an internal duplicate, report nothing)?" by comparing ONLY the file's NAME (`sfiii2.zip` → game "sfiii2"), without verifying whether it's the SAME physical path that actually claimed that game. Since the depth limit (§8) now allows the same filename to exist in more than one scanned folder, two physically distinct `sfiii2.zip` files (one real, one a duplicate in another folder) matched by name — and the duplicate was silently discarded as if it were "the same file, just with one extra copy inside" (the case this logic originally protected, e.g. `qsound_hle.zip` with `dl-1425.bin` duplicated INSIDE the same zip).

**Fixed:** now BOTH conditions are required to discard the attribution: (1) the file whose name matches the game is EXACTLY the same physical path that already claimed some rom for that game (`claimedArchiveURLsByGame`, a new index), AND (2) the surplus file's hash matches something that same game declares as its own (original check, preserved — without this, the real case of a clone's rom that actually belongs to its parent under Split would break, e.g. `sf2acc.zip` containing a `sf2ce` rom).

**Important — works across ANY configured ROM folder, not just within one:** `ROMMatcher.match` processes ALL files from ALL folders configured for a system in a single pass (`hashedFiles` already arrives combined from `FolderScanner.scan(paths:)`), so this fix detects duplicates regardless of which of the system's configured ROM folders each copy is in — explicitly verified with two independent folders (not nested within each other).

Verified live against the user's real case and with a new permanent test. `AuditReportDatabase.currentSchemaVersion` bumped to v16.

### 4e4. `optional="yes"` — MAME can run without this file (added Aug 5, 2026)

Second round of investigation (this time explicitly requested via web), after reviewing the DTD MAME embeds at the start of its own `-listxml` (the most authoritative reference possible — generated by MAME itself, not a third-party wiki). The DTD confirms a real, previously unconsidered attribute: `<!ATTLIST rom optional (yes|no) "no">` and the same for `<disk>`.

**Different from `nodump`:** `nodump` means "can't be verified" (no hash). `optional="yes"` means "MAME can run the machine without this file" — the file DOES have a real hash and is fully verifiable, it's simply not mandatory.

**Real usage in the DAT:** 0 roms, 3 disks (`cubeqst`, `cubeqsta`, `atronic`) — all with a real `sha1`. None of your current systems (CPS1-3/NEOGEO) use it.

**Implemented:**
- `DATRom.optional`/`DATDisk.optional`, parsed from the XML attribute.
- `AuditEntry.isOptional` — new field, persisted in SQLite (`is_optional` column, no need to invalidate old caches thanks to `DEFAULT 0`).
- Row text: "Missing (optional)" instead of plain "Missing" when a file declared optional is missing.
- `gameCategory(for:)`: a missing `optional` rom/disk no longer forces the game's aggregated state to red "Missing" — it follows the same non-severe reasoning as `.unverifiable`. If the game has other verified content, the badge stays green; if the only content is that missing optional disk, it falls back to "Correct" by default (same behavior that already existed for `.surplus`/`.unverifiable` with no other content).

**Additional bug found and fixed in the same pass:** `AuditReportDatabase.loadReport` never computed the `unverifiable` count when reloading a cached report from SQLite (it always stayed at 0 even though the individual entries had the correct status) — fixed alongside this change.

Verified live against the real DAT: `cubeqst.disks.first?.optional == true`, and auditing without the file produces `status=.missing, isOptional=true`. `AuditReportDatabase.currentSchemaVersion` bumped to v13.

### 4e3. `.unverifiable` extended to CHD disks (added Aug 5, 2026)

Investigation requested by the user after testing all three Rom merge mode modes: review the real DAT for other variables/special cases not yet considered. Found: **184 `<disk>` elements** in the real DAT (`mame0288.DAT`) declared without a `sha1` attribute — the exact equivalent of a `nodump` rom, but for CHD disks (e.g. `astron`, a Sega laserdisc, `<disk name="astron" status="nodump" .../>`).

**Before:** `CHDMatcher.match` did `guard let expectedSHA1 = diskSHA1 else { return .missing }` unconditionally — regardless of whether the real `.chd` file existed with the correct name, it was always reported "missing."

**Fixed:** same pattern applied to roms — if the disk declares no `sha1`, it's looked up by NAME (new `CHDDiskStatus.unverifiable(URL)` case); if a `.chd` with that name exists, it's reported as `.unverifiable` ("Nodump (unverifiable)") instead of `.missing`. If no file exists at all, it remains `.missing` (unlike a `nodump` rom, a disk IS still reported when missing — MAME normally needs the CHD to run the game, it's not optional like a never-dumped PAL chip).

**Additional adjustment needed:** `gameCategory(for:)` (per-game state aggregation) used to silently convert ANY non-severe state (missing/badDump/incorrect) to `.correct` — correct for roms (where `.unverifiable` almost always coexists with other verified roms), but incorrect for a disk whose ONLY state is `.unverifiable`: it would show a false "Correct." It now only falls back to `.correct` if there's at least one genuinely `.correct` entry; otherwise, if there's an `.unverifiable` entry, that's reported instead.

Verified with a synthetic case (an empty `.chd` file named `astron.chd`, since the user doesn't own that collection) against the real DAT: with the file present → `.unverifiable`; without it → `.missing` (sanity check). `AuditReportDatabase.currentSchemaVersion` bumped to v12 (no schema change needed, just invalidating the old cache).

### 4e2. New state: `.unverifiable` — `nodump` roms (added Aug 4, 2026)

**Real case:** `Neo-Geo MV-6F` didn't apply here, but a parallel case did: `Gryzor` (`gryzor.zip`, a clone of `Contra`) showed "Unknown game" (gray) in the list even though almost all its rows were yellow "Not needed here" — except one, `007766.20d.bin`, pure gray "Unrecognized."

**Root cause:** that rom is declared `status="nodump"` in the DAT — a PAL chip never dumped, no CRC/MD5/SHA1, just a `size="1"` placeholder. `contra` (the parent) and ALL its clones (including `gryzor`) redeclare the same name identically — there's no marker on the rom saying "this comes from such-and-such clone." The user had TWO physical copies of the same 1-byte placeholder (one in `contra.zip`, which satisfies the single deduplicated requirement; another in `gryzor.zip`, surplus). Since `nodump` has no hash, the existing "recognize surplus content by hash" mechanism (`romsByHash`) could never recognize that copy — it fell to pure "Unrecognized," indistinguishable from actual junk.

**Fixed with two complementary mechanisms:**
1. `DATGame.mergedFamilyMachineNames` (parent + all clones folded under Merged) — lets `ROMMatcher` claim an unclaimed `nodump` rom by NAME, searching in any archive belonging to the family, not just the game's own archive (covers the case "the real file only exists in the clone, never in the parent").
2. `SurplusFile.matchesNodumpRomName` — a surplus file with no known hash, but whose NAME matches a `nodump` rom in the DAT, is reclassified from `.surplus` to `.unverifiable` instead of staying "Unrecognized" (covers the real case found: a duplicate copy of the same placeholder).

**New `AuditStatus.unverifiable`:** gray (same color as `.surplus`), different icon (unfilled `questionmark.circle`), never raises severity (treated as `.surplus` in `AuditStatus.worst(among:)`). Row message: "Nodump (unverifiable)." An "Unknown game" bucket whose entries are ALL explained (whether via `requiredByGameDescription` or `.unverifiable`) is now reclassified to "Extra archive, not needed here" (yellow), same as the already-existing case of files 100% identified by hash.

Verified live against the real DAT and folder (`CAPCOM/OTHER`): `007766.20d.bin` in `gryzor.zip` went from `surplus` to `unverifiable`. `DATFileCache.currentFormatVersion` (v4) and `AuditReportDatabase.currentSchemaVersion` (v11) bumped.

### 4e. Real bug: duplicate declaration of the same rom within one machine (`mergedGame`, fixed Aug 4, 2026)

A real `-listxml` can declare the SAME physical rom (same name/crc/sha1/size) twice within a single `<machine>`, under different `region=` values. Confirmed live case: `neogeo` declares `sm1.sm1` once with `region="audiobios"` and again with `region="audiocpu"`, byte-identical — this isn't a malformed DAT, it's how the real dump is.

`splitGame()` already deduplicated this (its own comment cites this exact case), but `mergedGame()` — the function used under `mergeMode = .merged`, the user's actual mode — did not. Result: two logical requirements for a single physical file. One resolved to `.correct` (claimed the file), the other had nothing left to claim, fell through to the unrestricted `foundElsewhere` fallback, and found the same file already claimed — reporting `.incorrect` with `foundElsewhere` pointing at its OWN archive (`neogeo.zip`). This painted the game "Rom need fix" (yellow) in the list even though every visible rom row showed green "Ok" — because no individual row was wrong, the phantom duplicate entry was.

**This wasn't a message problem, it was a real requirement-counting bug.** Fixed by adding to `mergedGame()` the same "skip if an identical rom (name+crc+md5+sha1+size) was already added" guard that `splitGame()` already had. Verified live against the user's real NEOGEO DAT and folder: before, 35 entries for `neogeo` (one phantom `.incorrect`), after, 34 entries, all `.correct`.

Cache-busting applied (session rule): `DATFileCache.currentFormatVersion` 2→3, `AuditReportDatabase.currentSchemaVersion` 9→10.

## 7. Rom merge mode / Bios merge mode: what they mean, how ROMForge handles them, and which to use

Two **completely independent** axes (confirmed against a reference MAME frontend's real Settings dialog — neither implies nor conditions the other), each with the same three options (Merged / Split / Un-merged), applied to the ENTIRE MAME system equally (not configurable per game).

### 8a. Rom merge mode — what it physically does to files

| Mode | How the physical archive is organized |
|---|---|
| **Split** | A clone's archive contains ONLY what's unique to it; everything it shares with its parent (marked `merge="..."` in the DAT) is expected only in the parent's archive. |
| **Merged** | A SINGLE archive (the parent's) contains the parent's roms **and** all of the unique roms of each of its clones. Clones have no archive of their own. |
| **Un-merged** | Each machine (parent and every clone) has its OWN complete, self-contained archive — including both what it shares with the parent and what's unique to it. No archive depends on another. |

`MAMESetLayoutPlanner.swift` (`splitGame`/`mergedGame`/`nonMergedGame`) is where each is implemented — see each function's doc-comments for the exact detail, including the special cases already fixed (duplicate `merge=` roms within the same machine, full disk/rom family under Merged, etc. — sections 3 and 4e above).

### 8b. ROMForge's recommendation: **Un-merged**

It's the app's default (`MAMEMergeModeSettings.defaultMergeMode`, `GeneralSettingsView.swift`) and the one explicitly recommended in the Settings selector. Reasons:

1. **It's the mode with the fewest false "missing" reports.** Under Split or Merged, a game can depend on ANOTHER machine's archive existing (the parent, or vice versa) — if that other machine is missing or poorly organized, a game you do have is reported as incomplete when it really isn't. Un-merged eliminates that inter-file dependency entirely: each archive is audited 100% on its own.
2. **It's the most tolerant of partial or disorganized collections** — the most common real case (nobody has the complete MAME romset). With Split/Merged, having ONLY the clones you care about (without the parent) almost guarantees "incomplete"/"Bad" reports for roms you actually DO have, just expected in the wrong archive under that mode.
3. **It's the simplest to reason about:** "one file, one game, self-contained" — no need to understand the DAT's parent/clone relationship to know whether your collection is well organized.
4. **Real, non-hidden trade-off:** it uses more disk space (shared content duplicated in every archive). For ROMForge's user (collection auditing/management, not physical arcade cabinets with limited space), this is normally acceptable.

**When Merged can surprise you (warning already visible in the app):** with Merged, the parent's archive MUST also contain the unique content of each of its clones — if you only have the parent and none of its clones, the parent is reported incomplete, even though you never wanted those clones. Split doesn't have this problem (each clone is independent regarding what's its own), but it DOES require the parent's archive to be present for the shared content.

**Bios merge mode** follows the same table but applied specifically to BIOS roms (e.g. `neogeo.zip`) instead of the parent/clone relationship — Split (BIOS in a separate archive) is the most common convention in real collections and is ROMForge's default for this specific axis.

### 8c. Summary of MAME special cases already modeled by ROMForge

| MAME concept (real DAT attribute) | What it means | How ROMForge handles it | Section |
|---|---|---|---|
| `merge="..."` on `<rom>`/`<disk>` | This file is identical to one in the parent/BIOS — don't expect it here under Split | Filtered by `mergeName`/layout planner according to the active mode | 8a |
| `status="nodump"` on `<rom>` | Real chip never dumped — no hash, just a placeholder | `.unverifiable` if a file with the correct name exists (in the game's own archive or any archive of the merged family); if none exists, omitted from the report (MAME doesn't need it to run) | §4e2 |
| `status="nodump"` on `<disk>` | Same, but for CHDs | `.unverifiable` if a `.chd` with the correct name exists; if not, `.missing` (unlike a rom, a CHD is usually needed to run the game) | §4e3 |
| `status="baddump"` | Known but incorrect dump (per MAME itself) | `isBadDump`/`romDumpStatus`, shown as an informational suffix, independent of the local finding | §3d (`AuditEntry.isBadDump`) |
| `optional="yes"` on `<rom>`/`<disk>` | MAME can run the machine without this file, even though it's real and verifiable | "Missing (optional)" instead of "Missing"; doesn't force the game's badge to red | §4e4 |
| Exact duplicate rom within the same machine (same name+hash, two regions) | E.g. `neogeo`'s `sm1.sm1` (regions `audiobios` and `audiocpu`) | Deduplicated before generating requirements — a single entry, not two | §4e |
| `isdevice="yes"` with real roms | An internal MAME "device" that also has its own auditable romset (e.g. `qsound_hle`) | Audited as its own entry, not excluded just for being a device | investigated Aug 5, 2026, already fixed before |
| `<softwarelist>` inside `<machine>` | Which cartridge softwarelist(s) the driver supports | Pure metadata, no hashes — not parsed (doesn't affect file auditing) | investigated Aug 5, 2026 |
| `<sample>`/`sampleof` | Optional audio files (`.wav`) | Presence only (`hasSamples: Bool`) — individual sample files aren't audited | Already documented in `AuditReport.swift` |

## 8. Folder depth ROMForge scans

**Explicit rule (defined Aug 5, 2026, user's decision after evaluating alternatives — adjusted the same day after testing it live):** `FolderScanner` only descends **1 subfolder level** below the folder you configure for a system — the `<system>/<game>/<file>` convention (a loose file at the root, or inside exactly one game subfolder). If it finds a deeper subfolder, **it skips that entire subtree** (never enumerates its contents) and reports it in the Log panel ("Skipped (nested too deep, not scanned): ...") — the rest of the configured folder keeps scanning normally.

**Why (and why it does NOT abort the whole scan):** without a limit, pointing the app at a folder that's too broad (the disk's root, the user's home folder) would try to recursively enumerate EVERYTHING underneath — pointless and potentially very slow. The first version of this rule aborted the ENTIRE scan of the folder as soon as it hit a too-deep subtree — fixed live the same day after testing it: a single problematic subtree (e.g. `BATOCERA`) made the rest of an otherwise perfectly scannable folder unusable. Now only that subtree is skipped, point by point, without affecting anything else.

**Real case that motivated this:** the user's real CPS3 folder has a `BATOCERA` subfolder that duplicates several games one level deeper than allowed (`CPS3/BATOCERA/sfiii3/cap-33s-1.chd` = 2 levels, violates the 1-level limit). With the current rule, `BATOCERA` is simply omitted from the scan (logged, never enumerated) — the rest of CPS3 (`sfiii`, `sfiii2`, `sfiii3`, `sfiii3ur1`) scans normally. In fact, that same physical duplication was the root cause of the duplicate CHD bug fixed in §4e5 — by omitting `BATOCERA` from the scan, that duplication no longer appears either.

**Not to be confused with:** multiple ROM folders configured for the same system (e.g. one folder for NEOGEO and a separate one for its updates) — that's already supported independently of this and has nothing to do with this limit; the limit applies to depth WITHIN each configured folder, not to how many folders you configure.
